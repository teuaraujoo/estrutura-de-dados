APRENDIZADOS

1. Banco de Dados: SQL x NoSQL

1.1 SQL
- Dados estruturados.
- Caracteristicas:
  - schemas fixos;
  - transacoes;
  - queries complexas;
  - impedance mismatch: talvez uma requisicao seja mais dificil de salvar em tabelas SQL.
  - Exemplo: carrinho de compra com itens, metodo de pagamento, informacoes, nome etc.
- Principios ACID:
  - Atomicity: todas as transacoes sao executadas ou nenhuma e executada.
  - Consistency: ao final de cada transacao o banco estara em um estado consistente.
  - Isolation: se estiverem sendo executadas multiplas transacoes em paralelo, uma nao ira afetar a outra.
  - Durability: transacoes sao permanentemente mantidas caso o sistema falhe.
- Esses principios sao bons, porem falando em escalabilidade e dificil mante-los.
- Talvez fosse necessario fazer um cluster de bancos, mas e dificil garantir a consistencia dos dados e isso iria quebrar um principio.

1.2 NoSQL
- Dados nao estruturados.
- Caracteristicas:
  - schemas flexiveis;
  - escalabilidade horizontal, com clusters;
  - performance;
  - big data;
  - mais simples;
  - mais flexibilidade dos dados;
  - mais facil de fazer cluster, porque nao precisa seguir os principios ACID;
  - aplicacao de GraphDB.

2. PostgreSQL, Prisma e Modelagem

2.1 PostgreSQL
- Database first.
- Code first.
- Migrations first.

2.2 Types e entidades
- Ou cria o seu proprio tipo.
- Ou utiliza o tipo do proprio Prisma.
- Sem parametro, vem com `id`.
- Como parametro, por exemplo `updateInput`, vem sem o `id` e e mais permissivo.
- Mais facil de fazer `PATCH` / `PUT`.

2.3 Criacao de tabela: PostgreSQL vs MySQL
- Problema:
  - voce usou coisas que sao do MySQL no PostgreSQL;
  - `ENUM` direto;
  - `ON UPDATE CURRENT_TIMESTAMP`.
- Explicacao:
  - PostgreSQL nao aceita `ENUM` direto: precisa criar tipo ou usar `VARCHAR + CHECK`;
  - `ON UPDATE CURRENT_TIMESTAMP` nao existe: usa trigger.

2.4 Tipos NUMERIC: precision e scale
- `NUMERIC(1,5)`:
  - invalido, porque `scale > precision`.
- `NUMERIC(5,2)`:
  - ate: `999.99`;
  - minimo: `-999.99`.
- Regra:
  - `precision` = total de digitos;
  - `scale` = casas decimais;
  - inteiros = `precision - scale`.

2.5 Foreign key, cascade e restrict
- `ON UPDATE CASCADE`:
  - atualiza automaticamente nas tabelas filhas.
- `ON DELETE RESTRICT`:
  - impede deletar se tiver dependencia.
- Ideia:
  - `CASCADE` = automatico;
  - `RESTRICT` = protecao.

2.6 DESCRIBE no PostgreSQL
- Nao existe `DESCRIBE`.
- Alternativas:
  - `\d tabela`, no `psql`;
  - `information_schema.columns`, via SQL.
- Ideia:
  - CLI: rapido;
  - SQL: scripts e backend.

2.7 Verificar conexao com Render
- Como validar:
  - conferir host, por exemplo `render.com`;
  - rodar: `SELECT current_database(), current_user;`;
  - ver IP: `SELECT inet_server_addr();`.
- Dica:
  - se for `localhost`, nao e Render.

2.8 BIGSERIAL vs IDENTITY
- `BIGSERIAL`:
  - metodo antigo;
  - usa sequence solta.
- `IDENTITY`:
  - padrao moderno;
  - mais controle.
- Diferenca importante:
  - `GENERATED ALWAYS`: bloqueia insert manual;
  - `GENERATED BY DEFAULT`: permite insert manual.

2.9 CREATE INDEX
- O que e:
  - estrutura para acelerar consultas.
- Exemplo:
  - `CREATE UNIQUE INDEX ...`
- Faz duas coisas:
  - melhora performance;
  - impede duplicacao.
- Uso real:
  - agenda;
  - horarios;
  - reservas.
- Sem index:
  - o banco le linha por linha ate achar o que quer;
  - `SELECT * FROM users WHERE email = 'joao@cmf.com';`;
  - o banco percorre toda a tabela, ou seja, full scan.
- Com index:
  - o banco vai direto no ponto;
  - `CREATE INDEX idx_users_email ON users(email);`;
  - agora ele encontra direto.

2.10 Execute Query x Execute Script
- Execute Query (F5):
  - executa so o comando selecionado.
- Execute Script (F5 com script / botao especifico):
  - executa tudo em sequencia como um script completo.

3. Next.js, Rotas e Supabase

3.1 Modelo mental: Express x Next
- Voce esta vindo do modelo:
  - Express = 1 arquivo central controlando tudo.
- No Next, o modelo e:
  - Next = responsabilidades distribuidas por convencao.

3.2 App Router e file-based routing
- Aqui o Next usa:
  - App Router: subpastas dentro do `app` viram rotas;
  - file-based routing: roteamento baseado em arquivos;
  - uma pasta criada no Next vira automaticamente uma rota.
- Rotas de pagina:
  - `app/users/page.tsx` -> `/users`.
- Rotas de API, ou Route Handlers:
  - `app/api/users/route.ts` -> `/api/users`.

3.3 Server Components
- No App Router, por padrao, tudo roda no servidor.
- Exemplo:
  - `export default async function Page() { const data = await fetch(...); return <div>{data}</div>; }`
- Server Components:
  - podem acessar banco;
  - podem usar Prisma;
  - nao vao para o browser.

3.4 Client Components
- Quando voce precisa de:
  - `useState`;
  - `useEffect`;
  - eventos.
- Voce marca:
  - `"use client";`
- Exemplo:
  - `"use client";`
  - `export default function Button() { return <button onClick={() => alert("click")}>Click</button>; }`

3.5 Middleware
- Arquivo:
  - `middleware.ts`.
- Roda antes de tudo.
- Exemplo:
  - `export function middleware(request) { if (!isLogged) { return redirect('/login'); } }`
- Usado para:
  - autenticacao;
  - protecao de rotas;
  - logs.

3.6 Server Actions
- Voce pode chamar funcoes direto do front.
- Exemplo:
  - `"use server";`
  - `export async function createUser(data) { await prisma.users.create(...); }`
- Isso evita precisar de API route em alguns casos.

3.7 Supabase createClient
- `createClient` no Supabase e a funcao fundamental do SDK JavaScript usada para inicializar uma conexao segura entre sua aplicacao, frontend ou backend, e seu projeto Supabase.
- Ela utiliza a URL do projeto e uma chave API publica para autenticar requisicoes.
- Permite interacoes com:
  - banco de dados;
  - autenticacao;
  - armazenamento.

4. Status Code

4.1 401
- `401 -> Unauthorized`.
- Significa que a solicitacao nao foi processada porque o servidor nao autenticou o usuario.
- Pode ocorrer por:
  - ausencia de credenciais;
  - expiracao de credenciais;
  - erro nas credenciais, como login/senha ou token.

4.2 403
- `403 -> Unauthorized`.
- Acesso negado, proibido.

4.3 429
- `429 -> Too Many Request`.
- Indica que o cliente enviou um numero excessivo de solicitacoes ao servidor em curto periodo de tempo.

5. Seguranca

5.1 Headers de seguranca
- Headers de seguranca sao instrucoes que o servidor manda para o navegador dizendo como ele deve tratar a pagina.
- Eles ajudam a:
  - evitar execucao indevida de arquivos;
  - impedir que o site seja aberto dentro de iframe;
  - reduzir vazamento de informacao entre sites;
  - bloquear APIs do navegador que o sistema nao usa;
  - forcar HTTPS em producao.
- Em resumo:
  - headers nao substituem autenticacao e autorizacao;
  - headers fortalecem a seguranca no navegador;
  - headers sao uma camada extra de protecao.

5.2 Headers aplicados
- `X-Content-Type-Options`:
  - impede o navegador de tentar adivinhar o tipo do arquivo.
- `X-Frame-Options`:
  - impede abrir o site dentro de iframe.
- `Referrer-Policy`:
  - controla quanta informacao da URL anterior e enviada.
- `Permissions-Policy`:
  - bloqueia camera, microfone e geolocalizacao.
- `Strict-Transport-Security`:
  - forca uso de HTTPS, mas deve ser ativado so em producao com HTTPS.
- `Cross-Origin-Opener-Policy`:
  - isola melhor a janela do site.
- `Cross-Origin-Resource-Policy`:
  - impede outros sites de carregar recursos do seu dominio.
- `Origin-Agent-Cluster`:
  - melhora o isolamento da origem no navegador.
- `X-DNS-Prefetch-Control`:
  - desativa prefetch de DNS.
- `X-Permitted-Cross-Domain-Policies`:
  - bloqueia politicas antigas de plugins como Flash.
- `X-XSS-Protection`:
  - desativa filtro antigo de XSS do navegador.
- `Content-Security-Policy-Report-Only`:
  - testa CSP sem bloquear a aplicacao.
- `Cache-Control em /api`:
  - evita cache de respostas sensiveis das APIs.

5.3 X-Content-Type-Options
- Exemplo:
  - `{ key: "X-Content-Type-Options", value: "nosniff" }`
- Esse header diz ao navegador para nao tentar adivinhar o tipo real do conteudo quando ele ja foi declarado via `Content-Type`.
- Ajuda a impedir ataques de MIME sniffing, em que um arquivo aparentemente inofensivo acaba sendo interpretado como executavel.
- A recomendacao comum e exatamente `nosniff`.

5.4 X-Frame-Options
- Exemplo:
  - `{ key: "X-Frame-Options", value: "DENY" }`
- Esse header impede que sua aplicacao seja embutida em `iframe`, `frame`, `embed` ou `object` em outro site.
- O objetivo principal e reduzir risco de clickjacking.
- Clickjacking ocorre quando alguem coloca sua tela invisivel por cima de outra interface para induzir cliques.
- `DENY` e a opcao mais restritiva: bloqueia framing ate no mesmo dominio.

5.5 Referrer-Policy
- Exemplo:
  - `{ key: "Referrer-Policy", value: "strict-origin-when-cross-origin" }`
- Esse header controla quanto da URL anterior o navegador envia no header `Referer` quando o usuario navega ou faz requisicoes.
- Com `strict-origin-when-cross-origin`, em navegacao para o mesmo site o referrer pode manter mais contexto.
- Em requests cross-origin ele reduz para so a origem.
- Em downgrade de HTTPS para HTTP ele nao envia referrer.
- A OWASP recomenda essa politica como boa base atual.

5.6 Permissions-Policy
- Exemplo:
  - `{ key: "Permissions-Policy", value: "camera=(), microphone=(), geolocation=()" }`
- Esse header restringe o uso de certas APIs sensiveis do navegador.
- Com `camera=(), microphone=(), geolocation=()`, voce esta dizendo que nenhuma origem pode usar camera, microfone ou geolocalizacao nas paginas onde esse header for aplicado.
- Isso e bom quando o app nao precisa desses recursos.
- A propria OWASP usa esse padrao como exemplo de endurecimento.

5.7 Strict-Transport-Security
- Exemplo:
  - `{ key: "Strict-Transport-Security", value: "max-age=63072000; includeSubDomains; preload" }`
- Esse seria o header HSTS.
- Ele instrui o navegador a acessar o site so por HTTPS durante o periodo definido em `max-age`.
- `includeSubDomains` estende isso aos subdominios.
- `preload` e um sinal para possivel inclusao na lista de preload dos navegadores.
- Detalhe critico:
  - esse header so deve ser enviado em HTTPS;
  - navegadores ignoram HSTS quando ele vem por HTTP.
- Faz sentido ativa-lo em producao, mas nao em ambiente local sem HTTPS.

5.8 Rate limit
- Rate limit e uma protecao para limitar quantas vezes um cliente pode chamar determinada rota em um intervalo de tempo.

5.9 RBAC
- RBAC significa Role-Based Access Control ou Controle de Acesso Baseado em Funcao.
- E um metodo de seguranca que gerencia permissoes de usuarios com base em suas funcoes, ou roles, na organizacao.
- As permissoes nao sao gerenciadas individualmente.

5.10 ABAC
- ABAC significa Attribute Based Attribute Control.
- Gerencia atributos.
- Exemplo:
  - o usuario pode criar tal coisa?

5.11 Verificacao de Origin em rotas
- Metodos safe:
  - nao tem mudanca de estado;
  - apenas leitura.
- Metodos mutaveis:
  - possuem mudancas de estado.
- Logica pratica:
  - rotas `POST`, `PUT`, `PATCH`, `DELETE`: validar `Origin` faz bastante sentido;
  - sao rotas que alteram dados;
  - normalmente terao `Origin` disponivel no contexto do navegador;
  - a OWASP trata exatamente esses metodos como foco principal da defesa contra CSRF.
- Rotas `GET`:
  - em geral voce nao precisa fazer essa verificacao, desde que sejam realmente so de leitura;
  - `Origin` pode nao vir em `GET` same-origin;
  - exigir esse header em toda leitura pode gerar bloqueios falsos sem ganho real de seguranca.

7. System Design

7.1 Definicao
- System design e o processo de definir, decompor e orquestrar os principais elementos de um sistema de software.
- Envolve:
  - componentes;
  - interacoes;
  - dependencias.
- O objetivo e satisfazer requisitos:
  - funcionais;
  - nao-funcionais;
  - de negocio.

7.2 Disponibilidade / Availability
- O sistema deve permanecer sempre operacional e retornar a resposta de uma solicitacao do cliente.
- Sempre que qualquer usuario quiser usar o servico, o sistema deve estar disponivel e satisfazer a solicitacao do usuario.
- Sistemas ficam fora do ar, por exemplo ecommerce, e isso gera perda de faturamento.

7.3 Taxa de transferencia / Throughput
- A taxa de transferencia e uma das principais metricas para medir o desempenho de um sistema.
- E a quantidade de dados ou o numero de solicitacoes que podem ser processadas em um determinado periodo de tempo.

7.4 Latencia / Latency
- E uma medida do tempo de duracao para produzir o resultado.
- Tambem pode ser entendida como tempo de resposta de uma requisicao.
- Baixa latencia = bom desempenho e menor tempo de resposta.

7.5 Protocolos de rede
- HTTP.
- TCP.
- IP, incluindo IPv4 e IPv6.

7.6 Balanceamento de carga / Load Balancing
- Maquinas que distribuem a carga entre varios servidores.
- Load balancers sao usados para evitar:
  - ponto unico de falha;
  - indisponibilidade do sistema pela sobrecarga em um ou alguns servidores.
- Eles:
  - distribuem o trafego;
  - previnem falhas no servico;
  - contribuem para a confiabilidade do sistema;
  - atuam como gerenciadores de trafego;
  - ajudam na alta disponibilidade do sistema.

7.7 Proxies
- Proxy e um mediador entre cliente e servidor.
- Quando um cliente envia uma requisicao, ela passa pelo proxy e ele redireciona a requisicao para alcancar o servidor.
- Proxy direto:
  - atua como mascara para os clientes;
  - oculta a identidade do cliente para o servidor.
- Proxy reverso:
  - atua como mascara para os servidores;
  - oculta a identidade do servidor da resposta.

7.8 Escalabilidade em sistemas distribuidos
- Quanto mais usuarios, mais requisicoes.
- O sistema pode ficar lento, demorar para responder e ter desempenho afetado.
- Sistemas distribuidos:
  - colecoes de computadores independentes, conectados em rede, que atuam como um sistema unico e coerente para o usuario.
- Escalar:
  - envolve aumentar a capacidade do sistema para lidar com mais requisicoes.
- Escalamento horizontal:
  - envolve adicionar mais servidores para distribuir as solicitacoes;
  - adiciona varios servidores mais simples;
  - adiciona clones do mesmo servidor de servico lado a lado;
  - distribui solicitacoes com um balanceador de carga.
- Escalamento vertical:
  - aumenta a capacidade de uma unica maquina;
  - atualiza a maquina com mais recursos, como CPU, memoria e armazenamento;
  - o problema e que em algum momento voce nao ira conseguir aumentar mais a capacidade da maquina;
  - o custo e alto;
  - em caso de falha voce tera apenas 1 servidor.

7.9 Escalabilidade horizontal x vertical
- Escalabilidade envolve lidar com mais cargas de trabalho com baixo custo.
- Essas cargas de trabalho geralmente representam:
  - usuarios;
  - dados armazenados;
  - transacoes;
  - numero de requisicoes.
- Tudo isso esta relacionado ao crescimento sem afetar a experiencia do usuario.
- Metricas de escalabilidade:
  - mais volume de dados: crescimento da empresa, mais usuarios, mais produtos;
  - maior concorrencia: mais conexoes, threads, mensagens e fluxos de dados sendo processados em paralelo;
  - manipulacao de varias sessoes do usuario ao mesmo tempo;
  - em apps web, significa quantos usuarios podem interagir com o sistema ao mesmo tempo sem afetar sua experiencia;
  - maior taxa de interacao: mede a frequencia com que o usuario troca mensagem com os servidores;
  - a taxa de interacoes pode aumentar ou diminuir de acordo com o tipo de sistema.

8. Monolito, Microservices e Arquitetura

8.1 Monolito
- Um monolito e uma aplicacao onde todas as partes do sistema estao dentro do mesmo codigo e deploy.
- Partes do sistema:
  - rotas;
  - regras de negocio;
  - acesso ao banco;
  - autenticacao;
  - etc.
- Caracteristicas:
  - um unico backend;
  - um unico banco, geralmente;
  - comunicacao interna via funcoes, simples e direta.
- Vantagens:
  - simples de desenvolver;
  - facil de debugar;
  - ideal para sistemas pequenos e medios.

8.2 Microservices
- Nos microservices, o sistema e dividido em varios servicos independentes.
- Exemplos:
  - servico de usuarios;
  - servico de turmas;
  - servico de autenticacao.
- Cada servico roda separado e se comunica via rede:
  - HTTP;
  - filas;
  - eventos.
- Desvantagens:
  - alta complexidade;
  - comunicacao entre servicos;
  - gerenciamento de multiplos deploys.

8.3 Conclusao sobre monolito e microservices
- Para a maioria dos sistemas, monolito e a melhor escolha.
- Sistemas comecam simples e so evoluem quando necessario.
- No seu caso:
  - poucos usuarios;
  - baixa carga;
  - nao e necessario pensar em escala avancada agora.

8.4 Arquitetura x organizacao de pastas
- Arquitetura define como o sistema funciona e se organiza logicamente:
  - monolito ou microservices;
  - como os modulos se comunicam;
  - como os dados fluem;
  - como o sistema escala.
- Organizacao de pastas e apenas a representacao da arquitetura no codigo.
- Exemplos:
  - por dominio, como users e turmas;
  - por tipo, como services e repositories.
- Conclusao:
  - organizacao de pastas tem certa flexibilidade;
  - mas deve seguir principios como separacao de responsabilidades, clareza e baixo acoplamento.

8.5 Estado / State
- Estado representa os dados atuais do sistema.
- Exemplos:
  - usuario logado;
  - dados no banco;
  - token JWT;
  - sessao.
- Tipos:
  - persistente: banco de dados;
  - temporario: tokens e sessoes.
- No seu sistema, voce ja usa estado em:
  - PostgreSQL, para dados;
  - JWT, para autenticacao.

8.6 Concorrencia
- Concorrencia ocorre quando multiplas requisicoes acontecem ao mesmo tempo.
- Exemplos:
  - dois usuarios criando uma turma ao mesmo tempo;
  - dois usuarios tentando ocupar o mesmo horario.
- Problemas possiveis:
  - dados duplicados;
  - inconsistencia;
  - conflitos.
- Solucao:
  - uso de transacoes no banco;
  - exemplo: `prisma.$transaction(...)`.
- No seu sistema, voce ja utiliza concorrencia de forma segura com:
  - transacoes do Prisma;
  - validacoes antes de inserir dados.

8.7 Performance em sistemas com crescimento
- Quando o sistema cresce, por exemplo clinica com muitos pacientes, os principais pontos sao:
  - paginacao;
  - selecao de dados;
  - indices no banco;
  - filtros e busca.
- Paginacao:
  - evita retornar todos os dados;
  - exemplo: `GET /pacientes?page=1&limit=10`.
- Selecao de dados:
  - retorna apenas o necessario;
  - lista: dados simples;
  - detalhe: dados completos.
- Indices no banco:
  - melhoram a velocidade de busca;
  - exemplo: `CREATE INDEX idx_pacientes_cpf ON pacientes(cpf);`.
- Filtros e busca:
  - permitem encontrar dados sem carregar tudo;
  - exemplo: `GET /pacientes?search=nome`.

8.8 Resumo geral
- Monolito:
  - tudo em um sistema, que e seu caso atual.
- Microservices:
  - sistema dividido, nao necessario agora.
- Escala:
  - crescer conforme demanda.
- Arquitetura:
  - como o sistema funciona.
- Pastas:
  - como voce organiza o codigo.
- Estado:
  - dados atuais do sistema.
- Concorrencia:
  - multiplas requisicoes simultaneas.
- Performance:
  - foco em banco, paginacao e queries.

9. Infraestrutura: Load Balancer, Reverse Proxy, API Gateway, SSL, SSH e CDN

9.1 Load balancer
- Processo de distribuicao do trafego de rede entre um grupo de servidores de back-end.
- Gerencia as solicitacoes de forma eficiente, garantindo um servico rapido.
- Em caso de falha de um servidor, o balanceador de carga redireciona o trafego para outros servidores ativos.
- Quando um novo servidor entra no grupo, o balanceador de carga automaticamente comeca a rotear as solicitacoes para ele.
- Pode ser configurado para realizar verificacoes de integridade nos servidores de backend registrados.

9.2 Reverse proxy
- Funciona como um mediador entre clientes e servidores.
- Um proxy reverso fica a frente de um servidor de origem e garante que nenhum cliente se comunique diretamente com esse servidor de origem.
- Um site ou servico pode manter a confidencialidade dos enderecos IP de seus servidores de origem.
- O proxy reverso, por ser mais seguro e contar com mais recursos, oferece uma defesa aprimorada contra ataques ciberneticos.

9.3 API Gateway
- Versao expandida de um proxy reverso.
- Faz gerenciamento de APIs.
- Oculta dos clientes o particionamento do backend na arquitetura.
- Roteamento de solicitacoes:
  - direciona as solicitacoes recebidas para o servico relevante.
- Seguranca:
  - incorpora funcionalidades como autenticacao e autorizacao.

9.4 SSL
- Criptografia da comunicacao.
- HTTPS.
- Dados criptografados.

9.5 SSH
- Secure Shell.
- Acesso remoto seguro a servidores.
- Permite:
  - acessar maquina;
  - rodar comandos;
  - deploy manual.

9.6 CDN
- Content Delivery Network.
- Distribui conteudo globalmente.
- Faz cache de arquivos.
- Reduz latencia.
- Exemplo:
  - usuario no Brasil acessa o servidor mais proximo;
  - usuario nos EUA acessa outro servidor.

10. Dominio, Acoplamento e CQRS

10.1 Dominio
- Dominio e o problema que o sistema resolve.
- No projeto CMF:
  - o sistema nao e apenas um sistema com users, turmas e aulas;
  - ele e um sistema de gestao de escola / academia, CMF.
- O dominio envolve:
  - alunos;
  - professores;
  - turmas;
  - aulas;
  - frequencia;
  - agenda.
- Isso e o core do negocio.
- Caso tenha mudanca de toda a stack, o dominio continua o mesmo.
- O core do negocio nao muda.

10.2 Acoplamento
- Acoplamento e o quanto uma parte depende da outra.
- Alto acoplamento, ruim:
  - o service sabe detalhes internos do banco;
  - exemplo:
    - `const user = await prisma.user.findMany({ include: { turma: { include: { professor: true } } } });`
  - o service esta acoplado ao Prisma.
- Baixo acoplamento, bom:
  - exemplo:
    - `const user = await UserRepository.getWithTurma(id);`
  - o service nao sabe como funciona.

10.3 CQRS
- CQRS significa Command Query Responsibility Segregation.
- Separa operacoes de escrita de operacoes de leitura.
- Quando usar:
  - depende do dominio;
  - quando volume de read e maior que volume de write;
  - quando precisa de auditabilidade.
- Auditabilidade:
  - qualidade ou condicao de um sistema, processo ou registro que pode ser inspecionado, rastreado e verificado de forma independente.
- Command Side, escrita:
  - criar;
  - atualizar;
  - deletar;
  - validar regra de negocio.
- Query Side, leitura:
  - buscar dados;
  - listar;
  - montar projections;
  - dashboards;
  - relatorios.
- Beneficios:
  - escalabilidade;
  - performance;
  - organizacao.
- Escalabilidade:
  - pode ter banco so de leitura;
  - cache agressivo;
  - ElasticSearch;
  - Redis;
  - projections.
- Performance:
  - queries ficam ultra rapidas.
- Organizacao:
  - dominio separado da visualizacao.

10.4 Event Sourcing
- Event Sourcing armazena o estado de uma aplicacao como uma sequencia imutavel de eventos.
- Ele nao armazena apenas o estado atual.
- Beneficios:
  - historico completo;
  - auditoria;
  - replay;
  - integracao.
- Historico completo:
  - voce sabe quando aconteceu;
  - voce sabe quem fez;
  - voce sabe o que aconteceu;
  - auditoria perfeita.
- Auditoria:
  - muito usado em bancos, fintechs, ERPs e sistemas criticos.
- Replay:
  - voce pode reconstruir estado antigo.
- Integracao:
  - eventos podem alimentar filas, analytics, microsservicos e notificacoes.

11. Tipos de Deploy

11.1 Recreate
- Shutdown em uma versao e start na nova versao.

11.2 Rolling
- Cluster de servidores.
- Acontece a substituicao das versoes aos poucos.

11.3 Blue green
- Sobe a nova versao.
- Roda duas versoes.
- Faz substituicao de versao de forma sutil por redirecionamento de trafego.
- Rollback facilitado.

11.4 Canary
- Duas instancias rodando.
- Voce utiliza alguns usuarios como beta testers na versao nova.
- Redireciona o trafego de 5% dos usuarios para a versao nova.

11.5 Shadow
- Sobe a v2, mas os usuarios nao tem acesso.
- Acontece a duplicacao das requisicoes da v1 para a v2 para testes da v2.

12. ADR: Architecture Decision Records

12.1 Definicao
- ADR significa Architecture Decision Records.
- Sao registros de decisoes de arquitetura.
- E uma ferramenta para documentar e comunicar decisoes de design arquitetural em um projeto de software.

12.2 Boas praticas
- Padronizacao:
  - adote um formato consistente para seus ADRs;
  - incluir secoes como titulo, contexto, decisao, justificativa, alternativas consideradas e consequencias.
- Numero e rastreabilidade:
  - atribua um numero unico a cada ADR;
  - mantenha um registro desse numero em algum local de facil acesso.
- Versionamento:
  - mantenha uma versao clara e atualizada de cada ADR.
- Inclusao de justificativa:
  - nao apenas documente a decisao tomada;
  - explique por que essa decisao foi escolhida em vez das alternativas.
- Manutencao regular:
  - revise e atualize os ADRs periodicamente.
- Compartilhamento e acesso:
  - garanta que todos os membros da equipe tenham acesso facil aos ADRs.

12.3 Exemplo de ADR
- Numero do ADR: 001.
- Titulo: Escolha da Tecnologia de Banco de Dados.
- Data: 2023-08-13.
- Responsavel: Douglas Silva.
- Status: Aceito.

12.4 Contexto do exemplo
- No inicio do projeto de desenvolvimento do sistema de gerenciamento de inventario, foi necessario escolher a tecnologia de banco de dados que atenderia as necessidades da aplicacao.
- Diversas opcoes estavam disponiveis, incluindo bancos de dados relacionais e NoSQL.

12.5 Decisao do exemplo
- Foi decidido utilizar um banco de dados relacional para o sistema de gerenciamento de inventario.
- A tecnologia escolhida e PostgreSQL, devido a:
  - robustez;
  - suporte a transacoes ACID;
  - maturidade na comunidade de desenvolvimento.

12.6 Justificativa do exemplo
- Modelagem complexa de dados:
  - o sistema de gerenciamento de inventario envolve relacoes complexas entre produtos, fornecedores, pedidos e inventario;
  - um banco de dados relacional e mais adequado para modelar essas relacoes e manter a integridade dos dados.
- Transacoes e consistencia:
  - a precisao dos dados e crucial no gerenciamento de inventario;
  - transacoes ACID do PostgreSQL asseguram que as operacoes sejam consistentes e confiaveis.
- Suporte a escala futura:
  - inicialmente o projeto nao exige escalabilidade massiva;
  - PostgreSQL oferece a possibilidade de dimensionar verticalmente no futuro, se necessario, para lidar com aumento de volume de dados.
- Ferramentas e comunidade:
  - PostgreSQL possui ampla gama de ferramentas, documentacao e comunidade ativa.
  - Esses recursos podem ajudar a resolver desafios futuros.

12.7 Alternativas consideradas no exemplo
- MongoDB:
  - banco NoSQL amplamente usado para dados nao estruturados;
  - falta de suporte a transacoes ACID;
  - complexidade da modelagem de dados;
  - menos adequado para as necessidades do sistema de gerenciamento de inventario.
- MySQL:
  - banco relacional popular;
  - pelas caracteristicas especificas da aplicacao e pela necessidade de suporte aprimorado para operacoes complexas, PostgreSQL foi preferido.

12.8 Consequencias do exemplo
- Beneficios de banco relacional:
  - capacidade de realizar juncoes complexas;
  - garantir integridade referencial;
  - manter consistencia dos dados.
- Curva de aprendizado:
  - a equipe precisara se familiarizar com nuances especificas do PostgreSQL;
  - documentacao ampla e comunidade ativa sao recursos valiosos.
- Potencial de escalabilidade:
  - arquitetura relacional pode oferecer menos flexibilidade em escalabilidade horizontal em comparacao com algumas solucoes NoSQL.

12.9 Referencias citadas no exemplo
- Documentacao do PostgreSQL:
  - https://www.postgresql.org/docs/
- Comparativo entre bancos SQL e NoSQL:
  - https://www.sitepoint.com/sql-vs-nosql-differences/

13. Docker

13.1 Image
- Uma imagem Docker e como um modelo pronto da sua aplicacao.
- Contem:
  - seu codigo;
  - dependencias, como node_modules, libs etc.;
  - configuracoes;
  - instrucoes de execucao.

13.2 Container
- Container e uma imagem rodando como um processo isolado.

13.3 Dockerfile
- Arquivo de instrucoes para criar uma imagem.
- Define como montar a aplicacao.
- Exemplo:
  - `FROM node`: importando Node, a imagem base;
  - `WORKDIR /app`: trabalhando dentro do diretorio `/app`;
  - `COPY package.json /app`: copiando `package.json` para uma pasta `app` dentro do container;
  - `RUN npm install`: comando para gerar o build da aplicacao, instalando dependencias;
  - `COPY . /app`;
  - `CMD [ "node" , "index.js" ]`.

13.4 Comandos Docker
- `docker build -t node-application .`:
  - cria a imagem com o nome `node-application`.
- `docker run -p 3550:3550 node-application`:
  - cria o container e roda;
  - nesse caso o nome do container e aleatorio;
  - `-p 3550:3550` significa que a porta do computador e a mesma do container.
- `docker run -p 3550:3550 --name meu-container node-application`:
  - roda o container com nome fixo.
- `docker compose up`.

13.5 Docker Compose
- Ferramenta para rodar varios containers juntos.
- Exemplo:
  - `version: "3.9"` define a versao da sintaxe do Docker Compose;
  - `services:` define quais containers, ou servicos, a aplicacao vai ter.
- Exemplo de service:
  - `node-application:`;
  - `build: .`;
  - `container_name: node-application`, define o nome fixo do container;
  - `ports: - "3550:3550"`;
  - `restart: always`, se o container parar, sobe de novo automaticamente.
- Analogia:
  - Dockerfile = receita do prato;
  - Docker Compose = cardapio completo do restaurante.

14. Serverless, PaaS e Standalone Output

14.1 Serverless
- Serverless, ou computacao sem servidor, e um modelo de nuvem onde desenvolvedores focam no codigo.
- Provedores como AWS, Google e Azure gerenciam a infraestrutura.
- Cobranca ocorre apenas pelo tempo de execucao.
- Funcoes esporadicas ativadas por gatilho.
- Exemplo:
  - ativadas apenas quando sao usadas.

14.2 PaaS
- PaaS e um modelo de computacao em nuvem que fornece um ambiente completo.
- Inclui hardware e software hospedado pelo provedor.
- Permite que desenvolvedores criem, executem e gerenciem aplicativos pela internet sem manter servidores ou infraestrutura propria.
- Gerencia a infraestrutura.
- Voce so precisa subir o codigo.

14.3 Standalone output
- No contexto de desenvolvimento web, como Next.js, standalone output se refere a um artefato de build minimalista e independente.
- Ele inclui apenas os arquivos necessarios para rodar a aplicacao.
- Dispensa o `node_modules` completo.
- Otimiza containers Docker.
- Resulta em imagens menores e deployments mais rapidos em servidores.

15. Transacoes, Concorrencia e Isolation Level

15.1 maxAwait
- Tempo maximo esperando uma conexao/transacao disponivel.
- Exemplo:
  - se nao conseguir iniciar a transacao em 2 segundos, erro.

15.2 timeout
- Tempo maximo da transacao.

15.3 isolationLevel
- Define como transacoes enxergam outras transacoes.
- Em sistemas concorrentes:
  - duas pessoas podem modificar a mesma aula;
  - a mesma agenda;
  - o mesmo horario;
  - ao mesmo tempo.

15.4 Niveis principais de isolamento
- Read Uncommitted:
  - mais rapido;
  - mais perigoso;
  - pode ler dados sujos.
- Read Committed:
  - padrao do PostgreSQL;
  - le apenas dados commitados.
- Repeatable Read:
  - garante leituras consistentes.
- Serializable:
  - mais seguro;
  - simula execucao sequencial.

16. Termos de Uso, Politica de Privacidade e LGPD

16.1 Termos de uso
- Contrato.
- Delimita regras de uma plataforma/software.

16.2 Politica de privacidade
- Mostra o que e feito com os dados dos usuarios que acessam a plataforma.
- Relacionada a LGPD, Lei Geral de Protecao de Dados Pessoais.

16.3 Termos de adesao
- Termos de uso e politica de privacidade sao termos de adesao.
- Logo, nao precisam de assinatura.
- Basta o cadastro da pessoa na plataforma.
- Ajudam a evitar riscos trabalhistas, tributarios etc.

16.4 LGPD
- O orgao que coleta deve informar com transparencia qual dado sera compartilhado e com quem.
- Do outro lado, o orgao que solicita receber o compartilhamento precisa justificar esse acesso com base na execucao de uma politica publica especifica e claramente determinada.
- Deve descrever:
  - o motivo da solicitacao de acesso;
  - o uso que sera feito com os dados.

17. Big O, Complexidade e Memoria

17.1 Big O Notation
- Big O Notation e diferente de performance.
- Mede o quao bem o algoritmo escala em proporcao ao input.
- E eficiencia do codigo.
- Pergunta principal:
  - como esse codigo se comporta quando a quantidade de dados cresce muito?

17.2 Complexidades
- `O(1)`:
  - mesmo tempo independente do tamanho do input;
  - tempo constante.
- `O(log n)`:
  - busca binaria;
  - tempo logaritmico.
- `O(n)`:
  - para inputs pequenos e mais rapido;
  - para inputs grandes e mais lento;
  - escala na mesma proporcao do input;
  - tempo linear.
- `O(n2)`:
  - fica quadraticamente mais lento.
- `O(n log n)`:
  - `n x log n`;
  - para cada camada do problema, percorremos `n` elementos;
  - existem `log n` camadas;
  - complexidade linear logaritmica.

17.3 Complexidade temporal e espacial
- Complexidade temporal:
  - quanto tempo o codigo leva.
- Complexidade espacial:
  - quanta memoria o codigo usa.
- Alocar memoria:
  - reservar espaco na RAM.
- Usar memoria:
  - ocupar esse espaco com dados.

17.4 O que e memoria
- Quando o programa roda, vao para RAM:
  - variaveis;
  - arrays;
  - objetos;
  - funcoes.
- A RAM e como uma mesa de trabalho.
- Quanto mais coisas voce coloca nela, mais memoria usada.

17.5 Garbage Collector no JavaScript
- JavaScript possui um faxineiro automatico.
- Quando algo nao esta mais sendo usado, o JavaScript libera memoria sozinho.

18.1 Paginacao

- Idempotencia e a propriedade que garante que uma operacao, quando aplicada uma ou multiplas vezes, produz exatamente o mesmo resultado.
- Ela nao altera o estado inicial do sistema apos a primeira execucao.
